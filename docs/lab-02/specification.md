# Lab 2 Specification: Requester Ticketing System

## Overview
This specification defines the requirements, business rules, data model, and validation rules for the Requester-facing ticketing experience. The system allows requesters to create tickets, view their tickets, manage attachments, and track ticket status.

## Business Rules

### BR-01: Ticket Number Generation
The official Ticket Number is generated by the backend and must be unique. The format should be human-readable and sortable (e.g., TKT-000001).

### BR-02: Initial Ticket Status
A new Ticket begins with Current Status **New**. Status changes beyond "New" are excluded from Lab 2.

### BR-03: Development Requester Selector
Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication. This mechanism will be replaced with real authentication in Lab 3.

### BR-04: Ticket Ownership
A Ticket belongs to exactly one Requester. Only the owning Requester may view the Ticket Detail or manage its Attachments. The system must prevent one Requester from viewing another Requester's ticket.

### BR-05: Active Requester Requirement
Only active (non-inactive) Requesters may appear in the Development Requester selector. Inactive Requesters must not be able to create or access tickets through the selector.

### BR-06: Ticket Date Generation
The Ticket Date is automatically set by the backend to the current timestamp when the ticket is created and cannot be modified by the Requester.

### BR-07: Required Field Validation
All required fields must be validated on both frontend and backend. The system must not accept incomplete ticket submissions.

### BR-08: Category and Related System
Every Ticket must reference exactly one Category and exactly one Related System. Both must exist in the database and be active.

### BR-09: Ticket Summary Length
Ticket Summary must be between 10 and 200 characters after trimming leading and trailing whitespace.

### BR-10: Description Length
Ticket Description must be between 20 and 2000 characters after trimming.

### BR-11: Attachment Type Restriction
Only JPG/JPEG, PNG, WEBP, and PDF files may be uploaded as attachments. Other file types must be rejected with a clear error message.

### BR-12: Attachment Size Limit
Each attachment file must not exceed 5 MB. Oversized files must be rejected before upload begins.

### BR-13: Maximum Active Attachments
A Ticket may have at most five active (non-removed) attachments. Additional uploads must be prevented when the limit is reached.

### BR-14: Soft Attachment Removal
Attachment removal must be implemented as soft removal. Removed files remain in storage but are marked as removed, not deleted. Removed attachments must not be downloadable or previewable.

### BR-15: Attachment Removal Permission
Only the owning Requester may soft-remove attachments from their own tickets.

### BR-16: Attachment Removal Confirmation
Removal of an attachment requires explicit confirmation and an optional removal reason.

### BR-17: Failed Attachment Upload After Ticket Creation
If a Ticket is successfully created but subsequent attachment upload fails, the Ticket remains created. The Requester may retry attachment upload from the Ticket Detail screen.

### BR-18: Search Functionality
My Tickets must support text search across Ticket Number, Summary, and Description fields. Search is case-insensitive and matches partial strings.

### BR-19: Filtering
My Tickets must support filtering by Category, Related System, Current Status, and Requested Priority. Multiple filters may be applied simultaneously.

### BR-20: Sorting
My Tickets must support sorting by Ticket Date (newest first or oldest first) and Ticket Number. Default sort is Ticket Date descending (newest first).

### BR-21: Pagination
Ticket lists must be paginated. Default page size is 10 tickets. Supported page sizes: 10, 25, 50. The API must return total count and page metadata.

### BR-22: Empty State Display
When no tickets exist or search/filter returns no results, the UI must display a helpful empty state message guiding the Requester to create a ticket or adjust filters.

### BR-23: Error State Display
When API requests fail, the UI must display a clear, actionable error message. The system must preserve user-entered data after errors when possible.

### BR-24: Loading State Display
During API requests, the UI must show appropriate loading indicators to communicate that work is in progress.

### BR-25: Requester Switching
When switching the Development Requester, the system must clear the current ticket context and reload the new Requester's tickets. Unsaved data in Create Ticket form should trigger a confirmation dialog.

### BR-36: Download and Preview Security
Attachment downloads must verify ownership. Only the owning Requester may download or preview attachments. Removed attachments must not be accessible.

## Data Model

### Requester
Represents a person who submits tickets.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Int | Yes | Primary key, auto-increment |
| name | String | Yes | Full name of the requester |
| email | String | Yes | Email address, must be unique |
| isActive | Boolean | Yes | Whether the requester is active (default: true) |
| createdAt | DateTime | Yes | Timestamp when record was created |
| updatedAt | DateTime | Yes | Timestamp when record was last updated |

**Relationships:**
- One Requester may own many Tickets (one-to-many)

**Indexes:**
- Unique index on `email`
- Index on `isActive` for filtering active requesters

### Category
Represents ticket categories.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Int | Yes | Primary key, auto-increment |
| name | String | Yes | Category name, must be unique |
| isActive | Boolean | Yes | Whether the category is active (default: true) |

**Relationships:**
- One Category may be used by many Tickets (one-to-many)

**Seed Data:**
- Account and Access
- Hardware
- Software
- Network

### RelatedSystem
Represents specific systems, services, or platforms affected by tickets.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Int | Yes | Primary key, auto-increment |
| name | String | Yes | System name, must be unique |
| isActive | Boolean | Yes | Whether the system is active (default: true) |

**Relationships:**
- One RelatedSystem may be used by many Tickets (one-to-many)

**Seed Data (minimum 6):**
- Email
- Campus Wi-Fi
- VPN
- LEB2 App
- Grade Submission App
- Printer
- Corporate Laptop

### Ticket
Represents a support ticket created by a Requester.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Int | Yes | Primary key, auto-increment |
| ticketNumber | String | Yes | Official unique ticket number (e.g., TKT-000001) |
| requesterId | Int | Yes | Foreign key to Requester |
| categoryId | Int | Yes | Foreign key to Category |
| relatedSystemId | Int | Yes | Foreign key to RelatedSystem |
| summary | String | Yes | Brief summary (10-200 chars after trim) |
| description | String | Yes | Detailed description (20-2000 chars after trim) |
| requestedPriority | Enum | Yes | LOW, MEDIUM, or HIGH |
| currentStatus | Enum | Yes | Ticket status (default: NEW) |
| ticketDate | DateTime | Yes | System-generated creation timestamp |
| createdAt | DateTime | Yes | Record creation timestamp |
| updatedAt | DateTime | Yes | Record update timestamp |

**Relationships:**
- One Ticket belongs to one Requester (many-to-one)
- One Ticket references one Category (many-to-one)
- One Ticket references one RelatedSystem (many-to-one)
- One Ticket may contain many Attachments (one-to-many)

**Indexes:**
- Unique index on `ticketNumber`
- Index on `requesterId` for ownership queries
- Index on `ticketDate` for sorting
- Composite index on `(requesterId, ticketDate)` for My Tickets queries
- Index on `currentStatus` for filtering
- Index on `categoryId` for filtering
- Index on `relatedSystemId` for filtering

**Enums:**
- RequestedPriority: LOW, MEDIUM, HIGH
- TicketStatus: NEW (others excluded from Lab 2)

### Attachment
Represents files attached to tickets.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | Int | Yes | Primary key, auto-increment |
| ticketId | Int | Yes | Foreign key to Ticket |
| originalFilename | String | Yes | Original filename from upload |
| storedFilename | String | Yes | Sanitized unique storage filename |
| fileSizeBytes | Int | Yes | File size in bytes (max 5MB) |
| contentType | String | Yes | MIME type (image/jpeg, image/png, image/webp, application/pdf) |
| uploadedAt | DateTime | Yes | Timestamp when file was uploaded |
| isRemoved | Boolean | Yes | Soft removal flag (default: false) |
| removedAt | DateTime | No | Timestamp when file was removed |
| removalReason | String | No | Optional reason for removal |
| createdAt | DateTime | Yes | Record creation timestamp |
| updatedAt | DateTime | Yes | Record update timestamp |

**Relationships:**
- One Attachment belongs to one Ticket (many-to-one)

**Indexes:**
- Index on `ticketId` for retrieving ticket attachments
- Index on `isRemoved` for filtering active attachments
- Composite index on `(ticketId, isRemoved)` for active attachment queries

**Constraints:**
- Maximum 5 active (non-removed) attachments per ticket enforced by business logic

## Field Requirements and Validation

### Ticket Fields

#### Ticket Number (System-Generated)
- **Editable:** No (read-only, system-generated)
- **Required:** Yes (backend)
- **Format:** TKT-NNNNNN (zero-padded 6-digit number)
- **Validation:** Must be unique, generated by backend sequential counter or safe increment strategy
- **Frontend:** Display only, not editable

#### Ticket Date (System-Generated)
- **Editable:** No (read-only, system-generated)
- **Required:** Yes (backend)
- **Format:** ISO 8601 DateTime
- **Validation:** Set to current timestamp on creation
- **Frontend:** Display only, formatted for readability (e.g., "Jan 15, 2026, 2:30 PM")

#### Requester (System-Assigned)
- **Editable:** No (determined by Development Requester selector)
- **Required:** Yes (backend)
- **Validation:** Must be an active Requester ID
- **Frontend:** Display current selected Requester, not editable on form

#### Category (User-Selected)
- **Editable:** Yes
- **Required:** Yes
- **Frontend Validation:** Must select from dropdown of active categories
- **Backend Validation:** Must be valid active Category ID
- **Error Message:** "Please select a ticket category"

#### Related System (User-Selected)
- **Editable:** Yes
- **Required:** Yes
- **Frontend Validation:** Must select from dropdown of active related systems
- **Backend Validation:** Must be valid active RelatedSystem ID
- **Error Message:** "Please select the related system"

#### Summary (User-Entered)
- **Editable:** Yes
- **Required:** Yes
- **Min Length:** 10 characters (after trimming)
- **Max Length:** 200 characters (after trimming)
- **Trimming:** Frontend trims leading/trailing whitespace before validation and submission
- **Frontend Validation:** Character counter, real-time length validation
- **Backend Validation:** Reject if outside bounds after trimming
- **Error Message:** "Summary must be between 10 and 200 characters"

#### Description (User-Entered)
- **Editable:** Yes
- **Required:** Yes
- **Min Length:** 20 characters (after trimming)
- **Max Length:** 2000 characters (after trimming)
- **Trimming:** Frontend trims leading/trailing whitespace before validation and submission
- **Frontend Validation:** Character counter, real-time length validation
- **Backend Validation:** Reject if outside bounds after trimming
- **Error Message:** "Description must be between 20 and 2000 characters"

#### Requested Priority (User-Selected)
- **Editable:** Yes
- **Required:** Yes
- **Allowed Values:** LOW, MEDIUM, HIGH
- **Frontend Validation:** Must select one of three options (radio buttons or dropdown)
- **Backend Validation:** Must be valid enum value
- **Error Message:** "Please select a priority level"

#### Current Status (System-Assigned)
- **Editable:** No (system-controlled)
- **Required:** Yes (backend)
- **Initial Value:** NEW
- **Frontend:** Display only as badge
- **Backend:** Always set to NEW on creation in Lab 2

#### Attachments (User-Uploaded)
- **Editable:** Yes (can upload and soft-remove)
- **Required:** No (optional)
- **Allowed Types:** JPG, JPEG, PNG, WEBP, PDF
- **Max Size:** 5 MB per file
- **Max Count:** 5 active attachments per ticket
- **Frontend Validation:** File type checking, size checking before upload, count enforcement
- **Backend Validation:** MIME type verification, size enforcement, count enforcement, filename sanitization
- **Error Messages:**
  - "Only JPG, PNG, WEBP, and PDF files are allowed"
  - "File size must not exceed 5 MB"
  - "Maximum 5 attachments per ticket"
  - "Upload failed. Please try again."

### Validation Behavior After Failure

#### Frontend Validation Failure
- Highlight invalid field with error styling (red border)
- Display inline error message immediately below field
- Disable submit button until all validations pass
- Preserve all user-entered values
- Focus on first invalid field

#### Backend Validation Failure
- Return 400 Bad Request with structured error response
- Frontend displays backend error messages near relevant fields
- Preserve all user-entered data in form
- Allow user to correct and resubmit
- Do not clear form or navigate away

#### Network or Server Error
- Display error banner at top of form
- Preserve all user-entered data
- Provide "Retry" action
- Log error details for debugging
- Generic safe error message to user: "Unable to submit ticket. Please try again."

## Development Requester Selector

### Purpose
The Development Requester selector is a temporary testing mechanism that simulates a logged-in user without implementing authentication. It will be replaced with real authentication in Lab 3.

### Behavior
- Displayed as a standalone screen or persistent header component
- Shows dropdown of active Requesters (name and email)
- Selection persists in browser session/local storage
- Current Requester is displayed prominently in app header
- Requester may be switched at any time
- Switching Requester clears ticket context and reloads new Requester's data
- If unsaved data exists in Create Ticket form, prompt for confirmation before switching

### Loading Behavior
- On app load, fetch active Requesters from API
- If loading fails, display error message and retry option
- If no active Requesters exist, display message: "No requesters available. Please contact administrator."
- If no Requester is selected, prompt user to select one before accessing ticket features

### Storage
- Selected Requester ID stored in localStorage or session state
- On app reload, restore previous selection if still valid
- If previous selection is no longer active, clear and prompt for new selection

### Display
- App header shows: "Logged in as: [Requester Name] ([Email])"
- Include "Switch Requester" button or dropdown in header
- Development/testing indicator: "DEVELOPMENT MODE - Not Real Authentication"

## Database Design Decisions

### Decision: Soft Removal for Attachments
**Rationale:** Soft removal (isRemoved flag) instead of hard deletion provides:
- Audit trail for compliance and debugging
- Ability to recover accidentally removed files
- Preservation of historical data
- Protection against data loss
- Support for future features (e.g., IT Staff viewing removed attachments)

**Implementation:** Attachment records are never deleted. The `isRemoved` flag is set to true, and `removedAt` and `removalReason` are populated. Queries filter by `isRemoved = false` to show only active attachments.

### Decision: Composite Indexes for Query Performance
**Rationale:** My Tickets queries filter by `requesterId` and sort by `ticketDate`. A composite index `(requesterId, ticketDate)` optimizes this common query pattern, providing better performance than separate indexes.

**Implementation:** Prisma schema includes `@@index([requesterId, ticketDate])` on Ticket model.

### Decision: String-Based Ticket Number
**Rationale:** Although tickets are numbered sequentially, using a string field for `ticketNumber` allows:
- Human-readable format with prefix (TKT-000001)
- Future flexibility for different numbering schemes
- Natural sorting in UI
- No confusion between internal ID and user-facing ticket number

**Implementation:** Backend generates ticket numbers using a safe sequential strategy, formats with prefix and zero-padding, and stores as unique string.

### Decision: Separate Category and RelatedSystem Tables
**Rationale:** Categories and Related Systems are distinct concepts with different lifecycles and admin requirements. Separate tables allow:
- Independent management of each reference data type
- Different active/inactive states
- Clear semantic meaning in data model
- Future expansion with additional attributes

**Implementation:** Both are separate tables with many-to-one relationships to Ticket.
